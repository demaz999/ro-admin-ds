# AGENTS.md — инструкция для Codex (конвейер 2: витрина)

Репозиторий `ro-admin-ds` — кит 2: кодовая версия админского дизайн-кита Рососмотра. Тема на
токенах (Tailwind v4, `@theme`) плюс компоненты на shadcn-vue поверх Reka UI, Nuxt 4. Из
компонентов кита поштучно собираются страницы админки.

Этот файл самодостаточен: он описывает твою роль, зону, правила и процесс. Решение о втором
конвейере — владельца, 2026-09-15.

## 2. Зона

**Можно править только:**

- `app/components/showcase/**`
- `app/pages/index.vue`
- `app/pages/components/**` — страницы гайдов витрины (пилот — `/components/input`)
- `docs/showcase-*.md`

**Нельзя править** — это зона конвейера 1:

- `app/components/ui/**` — компоненты кита
- `app/assets/css/tailwind.css` — тема
- `docs/naming.md`, `docs/tokens.md`, `docs/handoff.md`, `docs/figma-fixes.md`, `docs/design-debt.md`
- `app/pages/**` кроме `app/pages/index.vue` и `app/pages/components/**` — страницы-стенды
  (`my-inspections.vue`, `insure-types.vue`, `statuses.vue`, `compare.vue` и будущие)
- `CLAUDE.md` и **этот файл** — `AGENTS.md` правит только конвейер 1; изменение предлагается
  строкой в `docs/showcase-requests.md` (раздел 4), закрывает конвейер 1

Если для витрины нужно что-то вне зоны — это запрос (раздел 4), а не правка.

Исключение со стороны конвейера 1: когда он меняет API компонента (пропсы, слоты, имена), он
механически правит примеры на витрине, чтобы она собиралась, и пишет об этом строку в
`docs/showcase-requests.md`. Оформление после такой правки — снова твоё.

## 3. Главное правило: витрина импортирует кит, а не повторяет его

Витрина показывает **настоящие компоненты кита** — `Button`, `Input`, `Table` и остальные из
`app/components/ui` — и никогда не воспроизводит их вёрстку у себя.

Изменение компонента в ките должно само отражаться на витрине. **Копия разметки или классов
компонента внутри витрины — дефект**, даже если сейчас выглядит одинаково: при следующей правке
кита витрина начнёт показывать то, чего в ките уже нет.

- Состояния показываются пропсами компонента (`disabled`, `invalid`, `variant`, `size`…), а не
  подкраской обёртки.
- Где компонент кита есть — используй его и для хрома витрины: таблицы, заголовки, подсказки.
- Чего в ките нет — собирай минимально на токенах темы и помни, что это хром витрины, а не
  компонент.

## 4. Документация — описательная

Витрина описывает кит **по факту кода и `docs/naming.md`**:

- назначение компонента;
- состояния;
- пропсы и слоты;
- примеры употребления и антипримеры — как не надо и почему.

**Правила витрина не устанавливает.** Если компонент расходится с `naming.md` или с макетом,
если не хватает пропа, слота или состояния — не чини кит и не обходи расхождение на витрине.
Запиши запрос в `docs/showcase-requests.md` строкой таблицы:

| Дата | Что нужно | Зачем | Статус |
|---|---|---|---|
| 2026-09-20 | у `Chip` нет состояния `disabled` в пропсах | показать выключенный фильтр на витрине | открыт |

Запросы закрывает конвейер 1 своими тактами.

## 5. Правила сборки витрины

**Значения — только из темы.**

- Цвета, тени, радиусы — через утилиты темы (`bg-primary`, `shadow-dropdown`, `rounded-md`) или
  `var(--token)`. Литералов hex, rgb и px в шаблонах и стилях нет.
- Кегли — только ступени кита: `text-3xs` 10/12, `text-2xs` 12/16, `text-xs` 13/16, `text-sm`
  15/20, `text-base` 16/20, `text-lg` 17/24, `text-xl` 20/24, `text-2xl` 24/28, `text-3xl` 32/36,
  `text-4xl` 36/40. Шкала Tailwind по умолчанию погашена — других кеглей нет.
- Начертания — 400, 500, 700. `font-semibold` запрещён: такого начертания у PT Root UI нет, браузер
  синтезирует его.
- Размеры и отступы кратны 4.

**Обе темы.** На витрине переключатель тем; всё, что ты делаешь, работает в `rososmotr` (рабочая)
и `atom` (сверочная). Значения меняются без перезагрузки: читай их в узле с темой, а не с корня
документа. Тема `viewapp` — пустой каркас, её не оформляй.

**Автопроверки `/compare` без регрессий.** Внизу `/compare` два раздела — «Автопроверка оптики
иконок» и «Автопроверка шрифтов». Базовая линия: **114 иконок и 361 текстовый узел, провалов нет**.
Падение счётчика или появление провалов — регрессия, PR с ней не отправляется.

**Витрина палитры: единица — строка, карточек нет** (правило `naming.md`, раздел 6). Токен
показывается строкой таблицы, группа — одной таблицей; свотч 64×40, радиус 8, обводка 1px внутрь
нейтральной рамкой на 50%; рампа состояний — сплошная полоса без зазоров.

**Практическое.**

- Запуск Codex: `npm run dev -- --port 3100` в локальной копии; витрина, автопроверки и скриншоты —
  только `http://localhost:3100/`. Порт `3000` занят конвейером Claude Code, Codex его не использует.
  Порт и локальная копия санкционированы владельцем.
- **Новый файл компонента требует перезапуска dev-сервера.** Автоимпорт Nuxt не подхватывает новый
  `.vue` на лету: компонент отрисуется нераспознанным тегом без ошибки в консоли. Проверяй поиском
  собственного тега в DOM на свежей вкладке.
- Внешний класс на компоненте кита сливается через его проп `class`, а не приклеивается рядом.
- Порядок вариантов Tailwind: состояние раньше псевдоэлемента — `hover:after:…`, не `after:hover:…`.

## 6. Голос витрины

Витрина пишется **для фронтенд-разработчика и дизайнера**, которые берут компонент в работу.

- Без ссылок на файлы, без упоминания ловушек, без истории решений и номеров тактов.
- Без имён переменных Figma и внутренних меток вроде `@debt`.
- Коротко и по делу: назначение одной фразой, «где применяется» — перечисление в именительном
  падеже: «пункт меню, строка таблицы, IconButton».
- Всё, что длиннее и про происхождение решений, остаётся в `docs/naming.md` и `docs/tokens.md`.

## 7. Процесс

**Ветка** — `codex/showcase` от `atom-base`. В `atom-base` напрямую не пушишь: вливание PR-ом после
приёмки владельца. Перед каждым PR ветка ребейзится на актуальный `atom-base`; правок `AGENTS.md`
PR не несёт — этот файл в зоне конвейера 1 (раздел 2).

### Текущая очередь

Блок временный: снимается тактом конвейера 1 по закрытию очереди. Живое состояние витрины —
`docs/showcase-state.md`, его ведёт Codex.

1. Пилот «Поле ввода» (`/components/input`) проходит стоп-точку вкуса владельца.
2. После «принято» — возврат к первой задаче из порядка работ ниже: `docs/showcase-concept.md`
   плюс один раздел.
3. Дописать в `docs/showcase-requests.md` запрос про `Dialog`: нет `DialogTitle` и

Провенанс: решение владельца. Замена первой задачи на гайд поля ввода была решением чата 2 без
согласования.

**Порядок работ.**

1. **Первый PR** — `docs/showcase-concept.md` (структура витрины, разделы, форма подачи, порядок)
   плюс **один раздел** витрины как превью концепции.
2. **Дальше — по одному разделу на PR**, и следующий начинается только после «принято» владельца
   по предыдущему.
3. **Сессии короткие:** один раздел за раз. Не набирай в одну сессию несколько разделов.

**Что лежит в каждом PR.**

- Скриншоты раздела при ширине **1280 и 1440**, в **обеих темах** — четыре снимка.
- Вывод обеих автопроверок `/compare`: число иконок, число текстовых узлов, провалы.
- Список изменённых файлов — все в зоне из раздела 2.

**Формат отчёта** — в описании PR и в ответе:

1. **«Решений: N»** — какие решения нужны от владельца, по каждому рекомендация и цена
   альтернатив. Ноль — так и пиши: «Решений: 0».
2. **Суть** — что сделано, с провенансом.
3. **«Смотреть глазами»** — адреса и состояния, которые стоит проверить глазом.
