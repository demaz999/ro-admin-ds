# Задание: строгий перенос Атома. Заменяет zadanie-pivot.md и поправку «оси, а не геометрия»

Решение по стоп-точке этапа 0: гибрид отклонён. Делаем чистый перенос Атома как
основу; всё наше — в архив до фазы обогащения. Это задание — полная формулировка
режима, при противоречии со старыми документами действует оно.

## Цель

Готовый профессиональный кит для сборки страниц: составы и матрицы — атомовские,
цвета и типографика — тема rososmotr, семантика имён — образцовая, потому что
эта веб-ДС станет эталоном, с которого дизайнеры соберут новую Figma-библиотеку.
Имена токенов, осей и компонентов в коде = будущие имена в Figma.

## Источники

- Состав, геометрия, матрицы, поведение: мастера Атома —
  https://www.figma.com/design/6IKVjTkdtKC232fZ0HR6uU/ (дубликат, узел 6001-53227).
- Тема rososmotr: текущие 78 токенов, 11 стилей, PT Root UI — не трогаются.
- Кит 1 и дашборд в этой фазе НЕ источники. Понадобятся в фазе обогащения.

## Архив наработок (ничего не удалять)

1. Создай ветку `atom-base` от текущего состояния; на main поставь тег
   `pre-atom` как снимок.
2. В `atom-base` перенеси наши компоненты кита 1 (InputField, SelectField,
   выпадашка, Tabs, Badge, Chip, StatusBadge, Button) в `archive/kit1-components/`
   с их эталонами из /compare: код сохраняется целиком, из витрины и реестра
   отключается. README в папке: что это, зачем, когда достаём (фаза обогащения).
3. Документы (open-questions, мапинг-таблицы, atom-audit, долг) остаются на месте
   как есть — это история решений, она действует.

## Темы

1. **rososmotr** — рабочая тема, значения не меняются. Приёмка компонентов
   Михаилом — в ней.
2. **atom** — сверочная тема: значения снимаются с атомовских мастеров ПО ХОДУ
   переноса каждого компонента и кладутся на наши семантические роли
   (--primary, --muted и т.д.), провенанс «сверочный, с мастера N, не для
   продакшена». Семантику Атома не раскапываем, дыры не решаем: чего мастер
   не показал — того в теме atom нет. Имена атомовских токенов (rocky, fargo
   и прочие фильмы) НЕ попадают в код нигде и никогда — ни в переменные,
   ни в комментарии, ни в значения осей.
3. **viewapp** — пустой каркас темы с TODO, значений нет.
4. Тёмная тема — после основы, отдельной задачей. Структура переключения
   свет/тьма × бренд закладывается сейчас (themes.md уже описывает).
5. /compare: сверка перенесённого ядра — в теме atom (родные цвета эталона,
   расхождение состава не путается с расхождением цвета); приёмочный просмотр —
   в rososmotr. Витрине — переключатель тем.

## Семантика имён (критическое требование)

- Значения variant, имена осей, слоты — канонические shadcn там, где есть аналог,
  наши по конвенциям — где нет. Кодовые имена Атома не переносятся.
- Заведи docs/naming.md — словарь ролей: каждая цветовая роль, расширение,
  типографический токен — одной строкой «что это и когда использовать».
  Пополняется с каждым компонентом. Это будущая дока для дизайнеров при переносе
  ДС в Figma — пиши для них, не для себя.

## Иконки

Только Google Material Symbols (fonts.google.com/icons), self-hosted. Пикты
Атома не используются нигде. Таблица «имя в ките/Атоме → имя Material Symbols»;
позиции без прямого аналога — списком Михаилу. Лесенка размеров — наша
(24 остаётся), лесенку Атома не берём.

## Порядок работ

1. Инвентарь Атома: перечень всех компонентов файла с node-id мастеров —
   в atom-audit.md, там же предложи разбивку на волны переноса (поля и кнопки
   первыми). Согласование разбивки у Михаила.
2. Первый компонент — Input: атомовское ядро целиком (вся матрица мастера,
   включая то, что у Атома существует только в документации, — если состояния
   есть лишь картинками, переносим как факт: ядро без них, строка в
   open-questions). Стоп-точка: /compare в теме atom + отчёт.
3. Дальше волнами по согласованной разбивке, стоп-точки по волнам.
4. Правила прежнего протокола действуют: не от скелета shadcn (Reka-примитивы
   и конвенции — можно, видимая часть — только с мастера), провенанс на каждом
   значении, computed-проверка шрифтов, «перенёс — обнови эталон», хардкод
   запрещён.

## Фазы после (фиксируем сейчас, делаем потом)

Фаза обогащения — только после приёмки основы Михаилом: достаём из архива наши
расширения (подпись/подсказка/счётчик полей, состояния error/pressed, Chip,
StatusBadge) и надстраиваем над атомовскими ядрами по одному, с эталонами из
кита 1. Пилотная страница «Мои осмотры» — после обогащения: на голых атомовских
ядрах она не собирается, это известно и нормально.
